# 架構圖

一張圖回答一個問題。答不出問題的圖讀者花了時間卻沒拿到原本不知道的事——目錄樹、元件清單、每個框都連到每個框，都屬於這類。

## 先寫下圖要回答什麼

動筆前用一句話寫下來。寫不出來就別畫。合格的問句：

- 這筆資料從哪來、經過誰、最後寫到哪？
- 改這個元件會波及哪些地方？
- 這個狀態怎麼轉移？哪些轉移不合法？
- 兩條方向相反的流程，邊界各自在哪？

「系統長什麼樣」不是問句。

## 格式：純文字區塊

```text
使用者輸入
     │ parse（cli.py）
     ▼
中介表示 ──── 驗證失敗 ───▶ 錯誤報告（exit 2）
     │ compile
     ▼
輸出檔案
```

純文字在終端、GitHub、各家 agent 都看得到，diff 得動，不需要 renderer。這是預設。

節點超過八個且邊會交叉、純文字排不開時，才換 mermaid，並在圖下方用一句話講清楚主幹，讓讀不到 renderer 的人接得上。

圖一律是文字。SVG、PNG 這類二進位檔 diff 不了，一定會跟程式碼脫節。

## 畫的時候

1. **只畫回答得到問題的元件。** 其餘刪掉，不是縮小字體塞進去。
2. **每條邊都掛動詞。** `投影`、`寫入`、`讀取`、`呼叫`、`回報`。裸箭頭只表示「有關係」，等於沒說。
3. **畫出返回邊與失敗邊。** 只有順利路徑的圖會讓人以為系統沒有錯誤處理。方向相反的兩條流程分開畫兩條邊，不用雙箭頭合併——合併會蓋掉「兩條路徑規則不同」這件事。
4. **框裡寫查得到的名字。** 檔案路徑、命令、子命令、schema 檔名。寫「驗證層」讀者查不到；寫 `python -m proj validate` 查得到。

## 圖放在擁有那個事實的文件裡

| 圖在講什麼 | 放哪 |
|---|---|
| 系統部件怎麼接起來 | 架構文件（`project-docs` 擁有） |
| 某個決定的前後對比 | 那份 ADR（`domain-modeling` 擁有） |
| 一個流程怎麼操作 | `README.md` 或對應的 skill |

圖跟解釋它的文字放在一起。獨立的圖檔資料夾會讓兩邊各自漂走，而且沒有擁有者。

## 收尾檢查

- 圖裡每個名字都 `rg` 得到。查不到代表圖在講一個不存在的東西。
- 圖與旁邊的表格、清單沒有講同一件事。重複的話留一個——通常留表格，圖只留表格表達不出的拓樸。
- 系統結構改動之後回來看這張圖：對不上就改，改不動就刪。過時的圖比沒有圖更貴。
