# 規範自檢

對照 `AGENTS.md` 檢查當前變更。先 `git diff` 看清楚範圍，再逐條走。

**逐條回報通過／不通過，不通過要指出 `檔案:行號`。不要只說「大致符合」。**

## 結構

- [ ] 有沒有新增空目錄，或只放一個檔的巢狀目錄？
- [ ] 有沒有預建但當下用不到的分層／抽象／介面／設定項？
- [ ] 模組邊界是依「會一起改變的理由」切的嗎？
- [ ] 變更之後產品仍然端到端可跑嗎？有沒有留下「之後才會接起來」的半成品？

## 入口與執行面

- [ ] 這次新增的操作有沒有製造第二個入口？
- [ ] 值得跑第二次的操作都有名字嗎？有沒有留下只存在於 scrollback 的呼叫？
- [ ] 新增的腳本是否封裝了固定多步驟流程？只包一個命令的要刪。
- [ ] 交付的指令是否一行可複製、不依賴環境變數前綴或當前目錄狀態？

## SSoT 與職責邊界

- [ ] 同一個事實有沒有被寫在兩個地方？
- [ ] issue 裡的 feature spec 有沒有被抄進 `docs/`？
- [ ] `docs/PROJECT.md` 有沒有混入 feature spec 或 task list？
- [ ] `CONTEXT.md` 是否仍是純詞彙表，沒有摻入實作細節？
- [ ] 依賴是否只在 `pyproject.toml` 宣告？

## 沿用與廢棄

- [ ] 有沒有自己實作了既有依賴或標準庫已經提供的東西？
- [ ] 被取代的舊路徑刪乾淨了嗎？有沒有留下相容層、fallback、註解掉的舊碼？
- [ ] 動到難逆的東西（對外契約、schema、持久化格式）時，是長期考量還是權宜方案？後者不接受，且理由要進 `docs/adr/`。

## 技能 vendoring

- [ ] 有沒有同一能力存在兩份實作？
- [ ] vendored SKILL.md 的 workflow 內文有沒有被改動？只允許出處 metadata 與設定檔引用的改寫。
- [ ] 每份 vendored skill 的 frontmatter 都有 `metadata.source` 與 `metadata.license` 嗎？
- [ ] 有沒有引用到沒被 vendor 進來的 skill？
- [ ] `LICENSES/` 有涵蓋所有 vendored 來源嗎？

## 變更範圍

- [ ] 這次 diff 是不是只有一個意圖？有沒有夾帶重構／格式化／依賴升級？
- [ ] 有沒有動到與任務無關的檔案？

## 顯性

- [ ] 有沒有隱藏依賴（全域狀態、環境變數未宣告、硬編路徑）？
- [ ] 有沒有未在文件說明的副作用？
- [ ] 有沒有 `latest` 或未釘選版本？鎖檔提交了嗎？

## 測試

- [ ] 這次有沒有動到對外契約？測試補了嗎？
- [ ] 修 bug 的話，有沒有一個會失敗的重現測試？
- [ ] 有沒有把契約測試當成行為測試在用？契約全綠不代表行為正確。
- [ ] 生成的產物（models 等）有沒有被手改？漂移檢查跑過了嗎？

## 安全與可逆

- [ ] 有沒有機密進了版控、日誌或 commit 訊息？
- [ ] 有沒有 SQL/Shell 的 f-string 拼接？這條不可豁免。
- [ ] 有沒有不可逆操作沒先確認？

## 例外

```bash
rg -n 'EXCEPTION:' --hidden --glob '!.git'
```

- [ ] 這次的每個規則偏離都有就地標註「理由 + 回收條件」嗎？
- [ ] 既有例外裡，有沒有回收條件已達成、該清掉的？

## 效能

- [ ] 有沒有沒量測就先做的優化？

## 判定衝突

依優先序：**安全與可逆性 > 契約穩定 > SSoT > YAGNI**。
「YAGNI 選最簡單」對上「架構決策看長期」時，用可逆性判準切。
權威順序只用於判斷現況與歷史，不用於決定該怎麼做事——現況違反規範是待修的偏離，不是先例。
判定完把理由講出來，不要只給結論。

## 輸出格式

```
通過：<條列>
不通過：<檔案:行號 — 違反哪條 — 建議怎麼改>
待決：<需要使用者判斷的取捨>
```
